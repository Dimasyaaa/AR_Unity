# Схема PostgreSQL и изменения базы

## Почему таблиц несколько

В базе девять таблиц с данными приложения и одна служебная таблица `app_schema_migrations`. Для реляционной схемы это небольшая структура: каждая таблица хранит свой тип данных, а внешние ключи связывают записи и защищают их целостность.

На снимке показаны `inventory_run_media`, но не `inventory_run_photos`. Поэтому после миграции общее число таблиц останется равным десяти: `inventory_run_media` заменится на `inventory_run_attachments`. Если в другой копии базы есть обе старые таблицы вложений, после объединения их станет на одну меньше. Удалять `app_schema_migrations` только ради числа в списке не стоит — это история схемы, а не рабочая таблица приложения.

```text
users ─────────────────────── inventory_runs ── inventory_run_items
                                  │
qr_codes ── cabinet_profiles ─────┘
                 ├─ cabinet_photos
                 └─ cabinet_checklist_items
inventory_runs ─────────────── inventory_run_attachments

users + qr_codes ─ inventory_sessions (журнал действий)
```

- `users` и `qr_codes` — сотрудники и значения QR-кодов.
- `cabinet_profiles` связывает QR-код со шкафом.
- `cabinet_photos` и `cabinet_checklist_items` хранят страницы шкафа и его актуальный список предметов.
- `inventory_runs` — завершённые проверки; `inventory_run_items` сохраняет ответы по каждому предмету на момент проверки.
- `inventory_run_attachments` хранит фотографии и необязательную голосовую запись.
- `inventory_sessions` связывает действия общего журнала с сотрудником и QR-кодом.
- `app_schema_migrations` хранит только версии применённых SQL-изменений, это не пользовательские данные.

Не следует объединять эти сущности в одну таблицу ради меньшего числа строк в списке: это усложнит связи, историю ответов и удаление зависимых данных.

## Применение изменений

SQL-файлы с номерами — журнал версий схемы. Сервер не выполняет их автоматически. Уже применённые файлы не удаляй и не запускай повторно произвольно: для текущей базы применяй только следующую неприменённую версию.

Для существующей базы при переходе на единую таблицу вложений:

1. Останови API, чтобы во время переноса не сохранялись новые отчёты.
2. Сделай резервную копию PostgreSQL штатным средством `pg_dump` или через pgAdmin.
3. В pgAdmin выбери именно базу, к которой подключён API, открой Query Tool и выполни целиком `009_inventory_run_attachments.sql`.
4. Проверь, что версия `009_inventory_run_attachments` появилась в `app_schema_migrations`, есть таблица `inventory_run_attachments`, а таблиц `inventory_run_media` и `inventory_run_photos` больше нет.
5. Запусти обновлённый API.

Миграция 009 переносит байты фото и аудио, сверяет перенесённые значения и только затем удаляет старые таблицы. Все действия находятся в одной транзакции. Если проверка не проходит, SQL завершается ошибкой, изменения откатываются, прежние таблицы остаются.

Минимальная проверка после применения:

```sql
SELECT version, applied_at
FROM app_schema_migrations
ORDER BY applied_at;

SELECT attachment_type, COUNT(*) AS attachment_count
FROM inventory_run_attachments
GROUP BY attachment_type
ORDER BY attachment_type;
```

`002_demo_cabinet_data.sql` предназначен для тестовых данных. Не запускай его на рабочей базе без необходимости.

## Вложения и голосовой комментарий

Новый отчёт из приложения отправляется после завершения чек-листа и добавления хотя бы одной фотографии. Поле `voiceBase64` может отсутствовать или быть `null`. Сервер сохраняет голос, только если он приложен, а админ-панель показывает аудиоплеер только для отчётов с записью. Старые отчёты без медиа остаются допустимыми для синхронизации с прежних версий приложения.
