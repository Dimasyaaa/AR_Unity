# Инвентаризация шкафов

## Сценарий в приложении

1. Пользователь входит в приложение и сканирует QR-код шкафа.
2. В `SampleScene` доступны три карточки: «Калькулятор», «Вид шкафа» и «Инвентаризация». Префабы Web и информации о продукции остаются в проекте для повторного использования.
3. Карточка «Вид шкафа» получает с API фотографии (лист 1 и лист 2) и позволяет переключать их.
4. Карточка инвентаризации загружает активный чек-лист с API. Для каждого пункта выбирают «Есть» или «Нет»; голосовые команды поддерживают «есть [название]», «нет [название]» и «сохранить».
5. Завершённая проверка сохраняется локально и сразу отправляется в API. Если сеть недоступна, локальная копия остаётся ожидающей синхронизации. Повторная отправка не создаёт дубль.
6. Администратор открывает вкладку «Инвентаризации», находит запись и просматривает пользователя, шкаф, время, итоги и статус каждого пункта.

QR-коды, которые не связаны с карточкой шкафа, продолжают открывать существующие листы продукции.

## Где находятся данные

- `cabinet_profiles` — шкаф, QR-код, название и совместимое поле главного фото (`BYTEA`).
- `cabinet_photos` — страницы фото шкафа 1 и 2, подписи, тип содержимого и сами изображения (`BYTEA`).
- `cabinet_checklist_items` — актуальный перечень предметов шкафа.
- `inventory_runs` — завершённые проверки с пользователем и временем.
- `inventory_run_items` — статус каждого предмета на момент проверки и его снимок названия.
- SQLite на устройстве хранит справочники и ожидающие синхронизации проверки, чтобы экран работал без сети.

Карточки в первую очередь читают данные и изображения через API. SQLite в `StreamingAssets` — стартовый офлайн-справочник для приложения; база в `persistentDataPath` также хранит локальную очередь инвентаризаций и QR-справочник для существующих сценариев. Изображения из `Assets/App/Content/CabinetPhotos` — исходные тестовые файлы для ручной загрузки через админку, они не подставляются в карточку автоматически. После загрузки изображений в PostgreSQL эти файлы можно удалить из проекта, если исходники больше не нужны.

## Заполнение шкафов в админке

1. Откройте вкладку «Шкафы» и нажмите «Добавить шкаф»; выберите свободный QR-код. Если QR-кода ещё нет, сначала добавьте его во вкладке «QR-коды».
2. Укажите название, загрузите фотографии листов 1 и 2 и впишите предметы: каждый с новой строки.
3. Нажмите «Сохранить шкаф». Настройки и фотографии приложение загружает через API; экспорт в SQLite нужен только для обновления локального офлайн-справочника.

В списке настроенных шкафов кнопка «Удалить шкаф» удаляет шкаф вместе с его QR-кодом, фотографиями, чек-листом, отметками и всей историей инвентаризаций. Такое же каскадное удаление сработает, если удалить привязанный QR-код во вкладке «QR-коды». Перед запросом показывается подтверждение; удаление выполняется целиком в одной транзакции PostgreSQL. Для QR-кодов без шкафа обычные события журнала сохраняются.

## Первичная настройка базы

1. Сделать резервную копию PostgreSQL.
2. Выполнить миграции `001_cabinet_inventory.sql`, `003_inventory_session_action.sql`, `004_cabinet_photo_pages.sql`, `005_calculator_action.sql` и `006_inventory_journal_backfill.sql` по порядку.
3. Только в тестовой базе дополнительно выполнить `Backend/Database/002_demo_cabinet_data.sql` после `001_cabinet_inventory.sql`; в рабочую базу тестовые данные не добавлять.
4. Заполнить фотографию и рабочие предметы шкафа в PostgreSQL, затем экспортировать SQLite.

Для печатного QR-кода используется обычный текстовый payload: сканер передаёт приложению именно строку из QR. Основной QR для демонстрации прокрутки — `DEMO-CABINET-002` (18 предметов). Тестовый короткий список на сервере привязан к `DEMO-CABINET-001`. Строка `DEMO-CABINET` без суффикса `-001` присутствует в одном локальном SQLite-справочнике, но не создаётся серверной тестовой миграцией; для сборки, работающей с API, её использовать не следует, пока такой код не добавлен на сервере и не связан там со шкафом.

Две тестовые фотографии находятся в `Assets/App/Content/CabinetPhotos/`; их источники и лицензия записаны рядом. Они нужны только как файлы для ручной загрузки листов 1 и 2 в админке и не кодируют QR. В проекте нет готовой картинки QR `DemoCabinet002.png` — QR нужно сгенерировать из точного текста `DEMO-CABINET-002` любым генератором QR-кодов.

В локальной тестовой базе чек-лист этого шкафа содержит «Веник», «Швабра» и «Ведро». Есть одна демонстрационная проверка пользователя «Тест МАУ»: веник и ведро отмечены «Есть», швабра — «Нет». Она нужна, чтобы сразу проверить список и подробности во вкладке «Инвентаризации»; это не реальный рабочий результат.

В Unity Editor сканер по умолчанию эмулирует `DEMO-CABINET-002`; поле `editorTestQrCode` в компоненте `QRScanner` можно переключить на `DEMO-CABINET-001`. Для калькулятора создана QR-запись `CALC_001`; после вычисления журнал получает действие `calc`, а сервер увидит его после синхронизации журнала.

Миграции и тестовые SQL-файлы не запускаются автоматически. Новая `006_inventory_journal_backfill.sql` добавляет в общий журнал старые проверки, которые уже были в `inventory_runs`, но не имели события `inventory_sessions`; повторный запуск не создаёт дубликаты. Перед применением проверьте целевую базу и сделайте резервную копию.

## API

- `GET /api/inventory/cabinets?qrCode=...` — карточка шкафа, список и доступные фото-листы.
- `GET /api/inventory/cabinet-photo?qrCode=...&pageNumber=1|2` — конкретная страница фото.
- `POST /api/sync/inventory-runs` — синхронизация завершённых проверок.
- `GET /api/admin/inventory/runs` и `GET /api/admin/inventory/runs/{id}` — список и подробности завершённых проверок для административной панели.

Маршруты уже включены в Swagger. Они требуют применения миграции до первого запроса с PostgreSQL.

## Ограничения текущего шага

- Приложение работает офлайн: после изменения перечня или фотографии в админке надо обновить SQLite экспортом и синхронизировать справочники на устройстве.
- Административные API текущего проекта не защищены серверной авторизацией. Не публиковать новые или существующие изменяющие маршруты в открытый интернет, пока не будет спроектирована проверка прав.
- Результаты синхронизации используют идентификатор пользователя SQLite как серверный `userId`, как и существующий API журнала. Для нескольких независимых баз пользователей позже нужно сделать надёжное сопоставление по уникальному идентификатору учётной записи.
